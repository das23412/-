# 发布检查清单（每次修改代码后必做）

> 背景教训：2026-08-29 的版本因为「CI 调试签名每次不同 + 版本号未变」，
> 导致用户无法覆盖安装、必须卸载旧版（丢失书架进度）。每次发版前逐条核对：

## 1. 版本号必须递增（必做）

发布新版本时需要同步改三处版本号：

1. `pubspec.yaml`：`version: 1.3.0+6`（三段语义版本 + 构建号，构建号每次 +1）
2. `lib/core/app_info.dart`：`version = '1.3.0'`、`build = '6'`（应用内“检查更新”用它对比）
3. 推送前打标签以自动发布 Release（应用内更新就查 Release）：
   ```bash
   git tag v1.3.0
   git push origin v1.3.0
   ```
   Actions 会自动构建并创建带 APK 附件的 GitHub Release。

## 2. 固定签名（已配置 ✓）

签名密钥已固定：`android/debug.keystore` 提交在仓库里，
CI 构建前会复制到 `~/.android/debug.keystore`，本地构建同理 ——
所有版本使用同一把签名，**可以互相覆盖安装**。

注意：
- 2026-08-29 之前的版本是 runner 临时签名，从旧版升级到 1.1.0+2 **还需要最后卸载一次**；
- 密钥库提交在公开仓库中，意味着任何人都能签出同签名的包 —— 对个人离线阅读器可接受；
  若日后上架商店，需换成私密正式密钥（走 GitHub Secrets 的 `MOYUE_KEYSTORE_BASE64` 流程，
  工作流已内置支持，配置后会优先使用）。

## 3. 发布流程

1. 改完代码 → `flutter analyze` + `flutter test` 本地过一遍；
2. 提交并推送（等 GitHub 连接窗口，重试 `git push`）；
3. 等 Actions 构建变绿；
4. 把最新一次 run 的 Artifacts → `moyue-apk` 链接发给用户；
5. 提醒覆盖安装即可（签名固定后不再需要卸载）。
